# Claude Code Best Practices — Research Notes

Compiled from official Claude Code documentation (code.claude.com/docs/en/) and secondary community sources (Reddit proved largely unreachable directly through available search tools — see Gaps section). Every claim below is attributed. This is a research reference only — no recommendations about applying it to any specific repo.

---

## 1. The core constraint: context window management

- Claude's context window holds the entire conversation — every message, file read, and command output — and performance degrades as it fills; Claude can start "forgetting" earlier instructions or making more mistakes as the window fills. [Best practices](https://code.claude.com/docs/en/best-practices)
- The context window is described as "the most important resource to manage." Tools for observing/controlling it: `/context` (see what's loaded), a custom status line, and the "Reduce token usage" strategies page. [Best practices](https://code.claude.com/docs/en/best-practices)
- Nearly all other best practices in the official docs are framed as corollaries of this one constraint (verification loops, subagent delegation, `/clear` discipline, CLAUDE.md size limits, skill progressive disclosure).

## 2. Verification loops ("give Claude a way to verify its work")

- Without a runnable check, "looks done" is the only signal Claude has, so the human becomes the verification loop. Giving Claude something that returns pass/fail (tests, build exit code, linter, a diff against a fixture, a browser screenshot comparison) lets Claude iterate to a real signal instead of a plausible-looking stop. [Best practices](https://code.claude.com/docs/en/best-practices)
- Four escalating ways to gate a stop on a check, from lowest to highest setup cost: (1) ask Claude to run the check and iterate within one prompt, (2) set the check as a `/goal` condition so a separate evaluator re-checks it every turn, (3) a **Stop hook** that runs the check as a script and deterministically blocks the turn from ending until it passes (Claude Code overrides the hook and ends the turn after 8 consecutive blocks), (4) a verification **subagent** or dynamic workflow that gives a fresh model a chance to refute the result, so the agent that did the work isn't the one grading it. [Best practices](https://code.claude.com/docs/en/best-practices)
- Ask Claude to show evidence (test output, command + result, screenshot) rather than asserting success — faster to review than re-running verification yourself, and it works for unattended sessions. [Best practices](https://code.claude.com/docs/en/best-practices)
- Adversarial review pattern: have a subagent review a diff in a *fresh* context (only the diff + criteria, not the reasoning that produced the change) before counting work as done. Bundled `/code-review` does this for correctness; for checking against a plan, name the plan, the edge cases, and "report gaps, not style preferences" explicitly. Docs warn that a reviewer prompted to find gaps will usually report *some* even when work is sound — chasing every finding leads to over-engineering, so tell the reviewer to flag only correctness/requirement gaps. [Best practices](https://code.claude.com/docs/en/best-practices)

## 3. Explore → Plan → Code → Commit workflow

- Recommended 4-phase flow: Explore (plan mode, `Shift+Tab` until "plan mode on", or `claude --permission-mode plan`) → Plan (ask for a concrete plan; `Ctrl+G` opens it in your editor for direct edits) → Implement (exit plan mode, code + verify against the plan) → Commit. [Best practices](https://code.claude.com/docs/en/best-practices)
- Explicit caveat: planning adds overhead and isn't always warranted. "If you could describe the diff in one sentence, skip the plan." Planning pays off when the approach is uncertain, the change spans multiple files, or you're unfamiliar with the code. [Best practices](https://code.claude.com/docs/en/best-practices)

## 4. Prompting patterns

- Prefer specific over vague prompts: scope the task (file + scenario + testing prefs), point to sources (e.g., "look through X's git history"), reference existing patterns in the codebase to imitate, and describe symptom + likely location + definition-of-fixed for bug reports. Vague prompts ("what would you improve here?") are still useful during open-ended exploration. [Best practices](https://code.claude.com/docs/en/best-practices)
- Rich content channels: `@file` references, pasted/dragged images, URLs (allowlist frequent domains via `/permissions`), piping data (`cat error.log | claude`), and letting Claude fetch its own context via Bash/MCP. [Best practices](https://code.claude.com/docs/en/best-practices)
- For larger features, have Claude *interview* you with `AskUserQuestion` before implementing, then write a complete spec to a file (e.g. `SPEC.md`) and start a **fresh session** to implement from the spec — clean context focused on implementation. The most useful specs name the files/interfaces involved, state what's out of scope, and end with an end-to-end verification step. [Best practices](https://code.claude.com/docs/en/best-practices)

## 5. CLAUDE.md — writing an effective one

### What it is / how it loads
- CLAUDE.md is read at the start of every session; delivered as a **user message after the system prompt**, not part of the system prompt — meaning it's advisory context, not enforced config, so compliance isn't guaranteed. [Memory](https://code.claude.com/docs/en/memory)
- Files load from the working directory **and every directory above it** at launch; nested CLAUDE.md/`.claude/rules/` files in subdirectories load **on demand** when Claude reads files there, not at launch. All discovered files are **concatenated**, ordered root → working directory, with `CLAUDE.local.md` appended after `CLAUDE.md` at each level. [Memory](https://code.claude.com/docs/en/memory)
- Locations, broadest → narrowest: managed policy (org-wide, IT-deployed, cannot be excluded) → `~/.claude/CLAUDE.md` (personal, all projects) → `./CLAUDE.md` or `./.claude/CLAUDE.md` (project, shared via VCS) → `./CLAUDE.local.md` (personal, project-specific, gitignored). [Memory](https://code.claude.com/docs/en/memory)
- Block-level HTML comments (`<!-- ... -->`) are stripped before injection into context — usable for maintainer-only notes that don't cost tokens (comments inside code blocks are preserved). [Memory](https://code.claude.com/docs/en/memory)
- Project-root CLAUDE.md survives `/compact` — Claude re-reads it from disk and re-injects it. Nested CLAUDE.md and path-scoped rules reload only as matching files are touched again; instructions given purely in conversation do **not** survive compaction unless written to CLAUDE.md. [Memory](https://code.claude.com/docs/en/memory)
- `@path/to/file` import syntax: relative paths resolve relative to the importing file (not cwd), imports can nest up to 4 hops, and import parsing skips fenced/inline code so wrapping a path in backticks prevents it from being imported. Imported files still load in full at launch — imports help organization, not context size. [Memory](https://code.claude.com/docs/en/memory)
- An import that resolves **outside the working directory** ("external") triggers a one-time approval dialog the first time Claude Code encounters it in a project; declining disables it silently thereafter. This exists specifically to guard against a committed project file importing something from outside the repo. [Memory](https://code.claude.com/docs/en/memory)
- Claude Code reads `CLAUDE.md`, not `AGENTS.md`. For repos that already standardize on `AGENTS.md` (or Cursor/Copilot/Windsurf/Cline rules), the documented interop pattern is either a plain `@AGENTS.md` import inside CLAUDE.md (with Claude-specific instructions appended below it) or a symlink `ln -s AGENTS.md CLAUDE.md` (symlinks need admin/dev-mode on Windows, so the import form is the portable option there). `/init` and `/import` also read these other formats when generating/merging. [Memory](https://code.claude.com/docs/en/memory)

### Size and structure guidance
- **Target under 200 lines per CLAUDE.md file.** Longer files consume more context *and* reduce adherence — this is stated as a hard-ish rule, not a soft suggestion, and repeated verbatim in [Features overview](https://code.claude.com/docs/en/features-overview) ("Rule of thumb: keep CLAUDE.md under 200 lines"). [Memory](https://code.claude.com/docs/en/memory)
- Litmus test for every line: **"Would removing this cause Claude to make mistakes?"** If not, cut it. [Best practices](https://code.claude.com/docs/en/best-practices)
- Include/exclude table from the official best-practices guide:

  | ✅ Include | ❌ Exclude |
  |---|---|
  | Bash commands Claude can't guess | Anything Claude can figure out by reading code |
  | Code style rules that differ from defaults | Standard language conventions Claude already knows |
  | Testing instructions and preferred test runners | Detailed API documentation (link instead) |
  | Repository etiquette (branch naming, PR conventions) | Information that changes frequently |
  | Architectural decisions specific to the project | Long explanations or tutorials |
  | Developer environment quirks (required env vars) | File-by-file descriptions of the codebase |
  | Common gotchas or non-obvious behaviors | Self-evident practices like "write clean code" |

  [Best practices](https://code.claude.com/docs/en/best-practices)
- Specificity is what makes an instruction stick: "Use 2-space indentation" beats "format code properly"; "Run `npm test` before committing" beats "test your changes"; "API handlers live in `src/api/handlers/`" beats "keep files organized." [Memory](https://code.claude.com/docs/en/memory)
- If Claude keeps skipping one instruction, add emphasis ("IMPORTANT") to *that line only* — emphasizing many lines makes none of them stand out. [Best practices](https://code.claude.com/docs/en/best-practices)
- If two rules contradict (including across nested CLAUDE.md files and `.claude/rules/`), Claude may pick one arbitrarily — periodic review for conflicts is recommended, and `claudeMdExcludes` lets a monorepo contributor skip other teams' irrelevant ancestor CLAUDE.md files. [Memory](https://code.claude.com/docs/en/memory)
- Treat CLAUDE.md like code: review it when things go wrong, prune regularly, verify changes actually shift behavior. `/doctor` proposes trims for a checked-in CLAUDE.md — cutting content derivable from the codebase (directory layouts, dependency lists, architecture overviews) while keeping pitfalls, rationale, and non-default conventions. [Best practices](https://code.claude.com/docs/en/best-practices) / [Memory](https://code.claude.com/docs/en/memory)
- Decision rule for "does this even belong in CLAUDE.md at all": add it when Claude repeats a mistake, a code review catches a knowledge gap, you retype the same correction across sessions, or a new teammate would need the same context. If an entry is a multi-step procedure or only relevant to part of the codebase, it belongs in a **skill** or a **path-scoped rule**, not CLAUDE.md. [Memory](https://code.claude.com/docs/en/memory)
- Check CLAUDE.md into git so the team can contribute — "the file compounds in value over time." [Best practices](https://code.claude.com/docs/en/best-practices)

### `.claude/rules/` (path-scoped instructions)
- For larger projects, split instructions into `.claude/rules/*.md`, one topic per file (`testing.md`, `security.md`), discovered recursively (subdirectories like `frontend/` allowed). Rules **without** `paths:` frontmatter load unconditionally, same priority as `.claude/CLAUDE.md`. Rules **with** `paths:` frontmatter (glob patterns, brace-expansion supported) load only when Claude reads a matching file — this is the mechanism for keeping CLAUDE.md itself small while still having deep guidance available on demand. [Memory](https://code.claude.com/docs/en/memory)
- Rules directories support symlinks (including a shared cross-project rules repo linked into multiple projects) and are resolved with circular-symlink detection. User-level rules (`~/.claude/rules/`) apply to every project and load *before* project rules (lower priority). [Memory](https://code.claude.com/docs/en/memory)
- Distinct from skills: rules load automatically based on file-path matching; skills load on invocation or when Claude judges the description relevant to the conversation. Use rules for standing per-filetype/per-directory conventions; use skills for task-specific procedures that don't need to be "on" every session. [Memory](https://code.claude.com/docs/en/memory)

### Auto memory (separate from CLAUDE.md)
- A second, Claude-authored memory system: `user`, `feedback`, `project`, `reference` memory types, stored per-repo at `~/.claude/projects/<project>/memory/`, indexed by a `MEMORY.md` (loaded in full, capped at 200 lines / 25KB) with individual topic files loaded on demand only. Claude explicitly skips saving anything derivable from the codebase or already covered by CLAUDE.md. [Memory](https://code.claude.com/docs/en/memory)
- Relevant distinction for kit design: CLAUDE.md is instructions *you* write and is enforced-by-convention only; a **PreToolUse hook** is the mechanism to actually block an action regardless of what Claude decides. [Memory](https://code.claude.com/docs/en/memory)

## 6. Skills — SKILL.md design

### Format & frontmatter
- Minimal required frontmatter is `name` + `description`; other documented fields: `disable-model-invocation` (hide from auto-invocation, still runnable via `/name` — for workflows with side effects like deploy/commit), `user-invocable: false` (inverse — Claude can auto-invoke, but no `/name` for the user; for background reference knowledge), `allowed-tools` / `disallowed-tools` (scope tool access for the turn the skill is active), `context: fork` (run the skill in an isolated subagent context), `paths` (glob-based auto-activation), `argument-hint`, `arguments` (named positional args used as `$name` in the body). [Skills doc via fetch] and confirmed in [Features overview](https://code.claude.com/docs/en/features-overview)
- Only `name`, `description`, `license`, `compatibility`, `metadata` are portable outside Claude Code itself (i.e., meaningful to other tools reading the same file format) — everything else (`allowed-tools`, `context`, etc.) is Claude-Code-specific behavior.
- Substitutions available in skill body and `allowed-tools`: `$ARGUMENTS`, `$0`/`$1`/positional, `$name` (named arg), `` ${CLAUDE_SKILL_DIR} ``, `` ${CLAUDE_PROJECT_DIR} ``, `` ${CLAUDE_SESSION_ID} ``, `` ${CLAUDE_EFFORT} ``.
- Dynamic context injection: `` !`command` `` placeholders inside a skill body execute once *before* Claude reads the skill and the literal command output (not the command itself) is substituted in — used to hand Claude live data (e.g. `git diff HEAD`) without it needing to run the command itself.

### Progressive disclosure (the core design principle)
- Only the `description` field loads into context on every turn; the full `SKILL.md` body loads **only when invoked**. This is the mechanism that keeps having many skills cheap. [Features overview](https://code.claude.com/docs/en/features-overview)
- Documented sizing guidance: keep `SKILL.md` itself under ~500 lines; move detailed reference material into separate files linked from the skill body (e.g. `[reference.md](reference.md)`) — Claude only reads those when referenced or asked for.
- Skill content, once loaded, **persists across later turns in the conversation** and is **not re-read** on subsequent turns; if invoked again with different args or updated dynamic-command output, the full content is re-appended. On compaction, skills forward to the next turn under a 5,000-token-per-skill cap and a 25,000-token budget across all skills — meaning an overly large skill can get truncated or dropped at compaction, another argument for staying well under the line-count guidance.
- Skill content should be written as **standing guidance**, not one-time procedural instructions, because it stays live in context for the rest of the conversation.

### Discovery, resolution, invocation
- Skill locations in priority order (earlier wins on name collision): enterprise/managed → personal (`~/.claude/skills/<name>/SKILL.md`) → project (`.claude/skills/<name>/SKILL.md`) → plugin (namespaced `/plugin-name:skill-name`). [Features overview](https://code.claude.com/docs/en/features-overview) states the layering as managed > user > project for skills specifically.
- Nested `.claude/skills/` in a monorepo subdirectory is addressable via a path-prefixed name (`/apps/web:deploy`) while the root-level skill keeps the bare name (`/deploy`).
- Invocation: Claude auto-invokes when the task matches `description` (unless `disable-model-invocation: true`); user invokes explicitly via `/skill-name [args]`; skills can be chained (`/skill-a /skill-b do XYZ`, up to 6 per message as of v2.1.199 per a secondary source — verify against current docs before relying on the exact version number).
- Because Claude's routing to a skill depends entirely on matching the task against `description`, a vague or overlapping description is a documented failure mode: "Claude may load the wrong skill or miss one that would help." [Features overview](https://code.claude.com/docs/en/features-overview)

### Skill vs CLAUDE.md vs rules vs subagent (decision framework, official)
The docs give an explicit comparison table (condensed): use **CLAUDE.md** for "always do X" rules needed every session; use **rules** (`.claude/rules/` with `paths:`) to scope CLAUDE.md-style content to specific files/directories so it doesn't cost context everywhere; use **skills** for reference material needed only sometimes, or invocable multi-step workflows (`/deploy`, `/review`); use **subagents** when the point is context *isolation* (a task that reads many files but should return only a summary), not just "another set of instructions." [Features overview](https://code.claude.com/docs/en/features-overview)

A skill can also combine with a subagent: `context: fork` runs a skill's own logic inside an isolated subagent context; conversely a subagent definition can `skills:`-preload specific skills into its own startup context. [Features overview](https://code.claude.com/docs/en/features-overview)

## 7. Subagents

### Format & frontmatter (`.claude/agents/*.md`)
- Required: `name`, `description`. Optional and documented: `tools` (allowlist), `disallowedTools` (denylist against the inherited pool, including MCP wildcard patterns like `mcp__*`), `model` (`sonnet`/`opus`/`haiku`/`inherit`/full model id), `permissionMode` (`default`/`plan`/`auto`/`acceptEdits`/`dontAsk`/`bypassPermissions`), `maxTurns`, `skills` (preload full skill content at subagent startup instead of relying on on-demand discovery), `mcpServers`, `memory` (`user`/`project`/`local` — gives the subagent its own persistent auto-memory directory, separate from the parent conversation's), `background`, `effort`, `isolation: worktree` (run in an isolated git worktree), `color`, `hooks` (subagent-scoped lifecycle hooks).
- Scope/priority order: managed settings → `--agents` CLI flag (session-only) → `.claude/agents/` (project, VCS-shared) → `~/.claude/agents/` (user, all projects) → plugin `agents/` directory.
- Invocation: natural language ("use the X subagent to..."), guaranteed `@`-mention (`@agent-name` or the `@"name (agent)"` typeahead form), or as the session-wide default main agent via `claude --agent name` / `"agent": "name"` in settings.
- Tool restriction is the main safety lever for subagents doing anything sensitive — the documented db-reader example pairs a `tools: Bash` allowlist with a `PreToolUse` hook that inspects the actual SQL and blocks non-SELECT statements, i.e. the subagent's own prompt ("only run SELECT") is advisory, the hook is the enforcement.

### Context isolation specifics
- A non-fork subagent starts with: its own system prompt (not Claude Code's), the task message it was given, CLAUDE.md files, git status, preloaded skills, and the agent roster (for cross-agent `SendMessage`) — but **not** conversation history, output style, or the parent's auto memory. The built-in `Explore` and `Plan` agents omit even CLAUDE.md and git status.
- A **fork** is the opposite: it inherits the parent's full conversation history and system prompt (this document's own tool list explicitly recommends forking "when the intermediate tool output isn't worth keeping in your context" — i.e. forks are for continuing your own reasoning off to the side, not for a genuinely independent worker).
- Limits: subagent descriptions collectively should stay under 15,000 tokens of context; default max 20 concurrent subagents (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`); default max 3 levels of subagent nesting (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`); plugin-defined subagents don't support `hooks`, `mcpServers`, or `permissionMode` fields.
- Explicit **when to use / when not to use** guidance: use subagents when the task produces verbose output you won't need again, is self-contained with a clear summary, needs enforced tool restrictions, or can run in parallel with other independent work. Avoid subagents when the task needs frequent back-and-forth, when phases share significant context, for quick targeted changes, or when full conversation history needs to stay visible.

## 8. Hooks — deterministic enforcement

- The single clearest line in the docs for deciding hook vs. instruction: **"Put guardrails in hooks. An instruction like 'never edit `.env`' in CLAUDE.md or a skill is a request, not a guarantee. A `PreToolUse` hook that blocks the edit is enforcement. If a rule must hold every time, make it a hook rather than a prompt instruction."** [Features overview](https://code.claude.com/docs/en/features-overview)
- Corollary decision rule from the trigger table in the same doc: "You want something to happen every time without asking" → write a hook. Everything else in that "build your setup over time" table maps a recognizable trigger to a specific extension mechanism (repeated mistake twice → CLAUDE.md line; repeated typed prompt → user-invocable skill; repeated multi-step playbook pasted into chat → skill; side task flooding conversation with unneeded output → subagent; second repo needing the same setup → plugin). [Features overview](https://code.claude.com/docs/en/features-overview)
- Hooks are user-defined commands/HTTP requests/MCP tool calls/LLM prompts/subagents that fire at lifecycle events across *all* Claude Code surfaces (terminal, IDE, desktop, web). [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Three firing cadences: once per session (`SessionStart`, `SessionEnd`), once per turn (`UserPromptSubmit`, `Stop`, `StopFailure`), per tool call (`PreToolUse`, `PostToolUse`, and failure/batch variants). Full event catalog is large — tool-execution events (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `PermissionRequest`, `PermissionDenied`), completion events (`Stop`, `StopFailure`), model-switch events, notification/display events, subagent/task events (`SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`), context/config events (`InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`), worktree events, compaction events (`PreCompact`, `PostCompact`), and MCP elicitation events. [Hooks reference](https://code.claude.com/docs/en/hooks)
- `InstructionsLoaded` specifically is called out as useful for **debugging** which memory files actually loaded, when, and why — recommended for diagnosing path-scoped rules or lazy-loaded nested files. [Memory](https://code.claude.com/docs/en/memory)
- Config format: `hooks.<EventName>[].matcher` (tool/agent-name string, exact/list/regex depending on characters used) + `hooks.<EventName>[].hooks[]` entries with a `type` (`command`, `http`, `mcp_tool`, `prompt`, `agent`), plus per-entry `if` (conditional gate keyed to a tool-pattern), `command`/`args`, `timeout`, `statusMessage`. [Hooks reference](https://code.claude.com/docs/en/hooks)
- Exit code contract for `command` hooks: `0` = success (stdout parsed as JSON for control fields if present), `2` = **blocking error** (prevents the action on blockable events), any other code = non-blocking error (stdout still parsed as JSON if valid). Blocking/allow/deny decisions ride in a `hookSpecificOutput.permissionDecision` (`allow`/`deny`/`skip`) JSON envelope on stdout. [Hooks reference](https://code.claude.com/docs/en/hooks)
- Path placeholders for hook commands: `${CLAUDE_PROJECT_DIR}` (project root at session start), `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` — the documented example for a project-committed hook always references its script via `${CLAUDE_PROJECT_DIR}/.claude/hooks/validate.sh` rather than an absolute path, which is the built-in portability mechanism for hook scripts specifically. [Hooks reference](https://code.claude.com/docs/en/hooks)
- Hook config can live at user settings, project settings (shared, VCS), project local settings (gitignored), managed policy, plugin `hooks/hooks.json`, or inline in a skill's/subagent's own frontmatter (`once: true` on a skill-scoped hook removes it after first successful run; subagent-scoped hooks only run while that subagent is active). Unlike skills/subagents/MCP (which override by name/priority), **hooks merge** — every hook registered from every source fires on its matching event. [Features overview](https://code.claude.com/docs/en/features-overview) / [Hooks reference](https://code.claude.com/docs/en/hooks)
- Debugging: `/hooks` browses all configured hooks read-only (event, matcher, handler, source file); `CLAUDE_CODE_DEBUG=1` gives detailed execution logs including which hooks matched, exit codes, timeouts, and JSON parse errors. [Hooks reference](https://code.claude.com/docs/en/hooks)

## 9. Plugins (packaging layer)

- A plugin is a directory with an optional `.claude-plugin/plugin.json` manifest (`name` becomes the skill namespace prefix, `description`, `version`, `author`) plus root-level `skills/`, `commands/` (legacy flat-file skills — new plugins should use `skills/`), `agents/`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `monitors/monitors.json`, `bin/` (added to Bash `PATH` while enabled — cannot be included in an org-directory-distributed plugin), and a plugin-level `settings.json` (only `agent` and `subagentStatusLine` keys apply, and this file's values take priority over `settings` in `plugin.json`). [Create plugins](https://code.claude.com/docs/en/plugins)
- Explicit, repeated **common mistake** warning: don't put `commands/`, `agents/`, `skills/`, or `hooks/` *inside* `.claude-plugin/` — only `plugin.json` goes there; the other directories are siblings of `.claude-plugin/` at the plugin root. [Create plugins](https://code.claude.com/docs/en/plugins)
- Plugin skills are **always namespaced** (`/plugin-name:skill-name`) specifically to avoid collisions when multiple plugins define same-named skills — contrast with standalone `.claude/skills/`, which is not namespaced and can therefore collide across projects/teams if names aren't distinct. [Create plugins](https://code.claude.com/docs/en/plugins)
- Documented migration path from standalone `.claude/` config to a plugin: copy `commands/`, `agents/`, `skills/` directories as-is; hooks specifically move from inline `settings.json` `hooks` block into a separate `hooks/hooks.json` file (same JSON shape, different container file). After migrating, remove the originals from `.claude/` — same-named project/user agents override same-named plugin agents, so the plugin version won't take effect until the standalone original is deleted. [Create plugins](https://code.claude.com/docs/en/plugins)
- `--plugin-dir ./path` (also accepts a `.zip`) is the documented local-dev/test loop, with `/reload-plugins` to pick up edits without restarting, and `claude plugin validate ./plugin` to run the same structural checks used in the community marketplace review pipeline before submitting. [Create plugins](https://code.claude.com/docs/en/plugins)
- "Start with standalone configuration in `.claude/` for quick iteration, then convert to a plugin when you're ready to share" is the docs' own recommended default ordering — i.e. plugin packaging is an explicit later step, not a starting point. [Create plugins](https://code.claude.com/docs/en/plugins)

## 10. Settings & permissions (portability-relevant)

- Settings precedence, highest to lowest: managed settings (org) → `claude --settings` (CLI, session) → `.claude/settings.local.json` (personal, project, gitignored) → `.claude/settings.json` (shared, project, VCS) → `~/.claude/settings.json` (personal, all projects). [Settings](https://code.claude.com/docs/en/settings)
- The documented split of responsibility: personal defaults you want everywhere → `~/.claude/settings.json`; anything the whole team should share (allowed commands, project hooks, approved MCP servers) → committed `.claude/settings.json`, "because the value is that it ships with the repo"; anything machine-specific or sensitive (a local path, a personal key) → `.claude/settings.local.json`, gitignored. (Source: community/secondary — [Vincent's Blog settings.json guide](https://blog.vincentqiao.com/en/posts/claude-code-settings-misc/), consistent with the official settings precedence doc.)
- Permission rules are tiered by tool type: read-only tools (file reads, Grep) never prompt within the working/additional directories; Bash commands prompt unless in a built-in read-only allowlist, and a "yes, don't ask again" answer is remembered permanently per-repository-and-command. [Permissions](https://code.claude.com/docs/en/permissions)
- **Portability gotcha, confirmed via a live GitHub issue**: relative permission-pattern matchers don't reliably match against the absolute tool paths Claude Code actually invokes internally, i.e. a permission rule written with a relative path can silently fail to match once the tool resolves an absolute path — filed as [anthropics/claude-code#18200 "Relative path permission patterns don't match absolute tool paths"](https://github.com/anthropics/claude-code/issues/18200). This is a concrete, currently-open portability sharp edge for any settings.json meant to be pasted into other repos.
- Related, separate portability gotcha reported in a third-party issue tracker: a repo's committed `settings.json` should not embed **absolute paths to the repo itself** in hook commands, since that breaks for every other developer's checkout path — cited example: [tirth8205/code-review-graph#558](https://github.com/tirth8205/code-review-graph/issues/558) (third-party repo, not Anthropic's, but documents the same class of failure the official docs solve for via `${CLAUDE_PROJECT_DIR}`).
- Sandboxing (OS-level filesystem/network isolation, `/sandbox`) and "auto mode" (a classifier model reviews most actions instead of prompting a human, blocking scope escalation / unknown infrastructure / hostile-content-driven actions) are the two documented mechanisms for reducing permission-prompt friction without giving up control. [Best practices](https://code.claude.com/docs/en/best-practices)

## 11. CLI / automation-relevant patterns

- `claude -p "prompt"` runs non-interactively (for CI, pre-commit hooks, scripts); output formats are plain text, `json` (single object with a `result` field), or `stream-json` (one JSON object per line). A non-interactive run still creates a resumable session unless `--no-session-persistence` is passed. [Best practices](https://code.claude.com/docs/en/best-practices)
- Fan-out pattern for large mechanical migrations: have Claude write the list of target files to a file, then a shell loop calls `claude -p "..." --allowedTools "Edit,Bash(git commit *)"` per file — `--allowedTools` is explicitly called out as mattering more once you're running unattended. The bundled `/batch <instruction>` skill automates this same fan-out (5–30 subagents, each in its own worktree, each opening a PR) without a hand-written loop. [Best practices](https://code.claude.com/docs/en/best-practices)
- Writer/Reviewer pattern across two sessions (one implements, a second reviews the diff with fresh eyes because "a fresh context improves code review since Claude won't be biased toward code it just wrote") is presented as the canonical multi-session quality pattern, distinct from single-session self-review. [Best practices](https://code.claude.com/docs/en/best-practices)

## 12. Common failure patterns (named directly in the docs)

From [Best practices § Avoid common failure patterns](https://code.claude.com/docs/en/best-practices):

| Pattern | Symptom | Documented fix |
|---|---|---|
| The kitchen sink session | Unrelated tasks interleaved in one conversation | `/clear` between unrelated tasks |
| Correcting over and over | Same correction repeated, context fills with failed approaches | After 2 failed corrections, `/clear` and write a better initial prompt incorporating what was learned |
| The over-specified CLAUDE.md | File too long, Claude ignores half of it | Ruthlessly prune; convert always-correct behavior into deletion or a hook instead of a written rule |
| The trust-then-verify gap | Plausible-looking implementation misses edge cases | Always provide a verification mechanism; "if you can't verify it, don't ship it" |
| The infinite exploration | Unscoped "investigate X" fills context reading hundreds of files | Scope investigations narrowly, or push them into a subagent |

## 13. Community / secondary-source signal (see Gaps — Reddit itself was not directly reachable)

- A widely-repeated community framing (traced to a Threads repost of what it attributes to Anthropic's internal guidance, echoing the official docs' own CLAUDE.md guidance): treat every CLAUDE.md line as a decision Claude could not reverse-engineer from the code; if it's reverse-engineerable, it's excluded by default. [Threads repost](https://www.threads.com/@jatinw21/post/DU5o6EpiU9i/) — this is consistent with, and appears derivative of, the official Include/Exclude table in §5 above, not new information.
- Community and semi-official sources describe subagents as running with a roughly 200k-token isolated context each and note the recurring theme that "context rot" (degradation as context fills, with earliest instructions fading first) is the actual mechanism subagents are used to avoid — matches the official framing in §1/§7 but adds the "earliest instructions fade first" detail as an interpretive gloss rather than a documented Anthropic claim. [InfoQ summary of subagents](https://www.infoq.com/news/2025/08/claude-code-subagents) (secondary source, unverified against primary Anthropic material).
- A frequently repeated community troubleshooting note (multiple blog/dev.to sources, not Reddit specifically) is that CLAUDE.md instructions "go stale" as a project evolves and that some practitioners build a self-review skill that periodically re-audits CLAUDE.md against recent conversations/PRs to catch drift — this is a workflow pattern layered on top of the official `/doctor` trim-proposal feature (§5) rather than something the official docs describe themselves.
